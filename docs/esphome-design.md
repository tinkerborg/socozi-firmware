# ESP32 bridge — design

An ESP32-C3 wired to the chair's SWD pins, running ESPHome, so the chair shows
up in Home Assistant and can be reflashed without opening it up again.

Implemented. `make esp` builds it; §9 says what has and has not been proven.

## 1. What the ESP is attached to

| | |
|---|---|
| Board | Seeed XIAO ESP32-C3 |
| Power | chair J12, permanently-live 5 V and ground, into the XIAO's 5 V pin |
| SWCLK | D4 (GPIO6) → PA14, 100 Ω in series |
| SWDIO | D5 (GPIO7) → PA13, 100 Ω in series |
| Ground | common |

The series resistors exist so the Bus Pirate can be clipped on while the ESP is
still wired: whichever side is driving wins, and neither can source enough
current through 200 Ω to damage the other.

Both parts run 3.3 V logic from their own regulators, so there is no reference
voltage to arrange. On the bench the ESP runs from USB-C and the Bus Pirate
supplies the chair board's 3.3 V; in the chair the ESP takes 5 V from J12 and
makes its own 3.3 V. The two 3.3 V rails never meet.

Strapping pins D0 (GPIO2), D8 (GPIO8) and D9 (GPIO9) are avoided, as is D6
(GPIO21), which the ROM bootloader talks on at reset.

## 2. How the ESP reads the chair

Not over the console, and not by parsing text. The chair already publishes its
entire live state as a plain C struct pinned to the base of SRAM:

    volatile struct debug_block dbg  @ 0x20000000

SWD's access port does its own bus transactions, independent of the core, so
reading that struct does not halt the chair, does not perturb timing, and cannot
starve the watchdog. The firmware only ever writes the block — nothing in it
feeds back into behavior — so a bad read is a bad reading, never a bad chair.

The ESP therefore does, once per poll interval:

1. Select the AHB access port, 32-bit, auto-increment.
2. Write TAR = 0x20000000.
3. Read `sizeof(struct debug_block) / 4` words out of DRW.
4. Check word 0 is `DEBUG_MAGIC`; discard the read if not.
5. Publish changed fields to Home Assistant.

At a conservative 500 kHz bit-banged clock that is a few milliseconds per poll
for ~50 words. Default interval 1 s, configurable in YAML.

### Keeping the struct layout honest

The ESP must not carry a hand-copied idea of where `pos_recline` lives. The
struct is `#if`-guarded on the `ENH_*` flags, so its layout is a property of a
particular firmware build, not of the source tree.

So the firmware build generates the layout. `tools/gen-dbg-layout.c` includes
`debug.h`, is compiled by the *host* compiler with the same `-DENHANCED=` and
`ENH_*` settings as the target build, and prints a header:

```c
/* Generated by tools/gen-dbg-layout.c. Do not edit. */
#define SOCOZI_DBG_BASE   0x20000000u
#define SOCOZI_DBG_MAGIC  0x44424730u
#define SOCOZI_DBG_WORDS  52
#define SOCOZI_OFF_magic            0
#define SOCOZI_OFF_ticks            1
...
#define SOCOZI_OFF_pos_recline      46
```

Word offsets, not byte offsets: every field in the block is a `uint32_t`, so the
ESP indexes an array. A field that is compiled out gets no `SOCOZI_OFF_` at all,
so the component's `#ifdef` on it is the same question as "does this build have
it" — there is no separate `HAVE` flag to fall out of step.

`offsetof` from a real compile is the authority. No DWARF parsing and no second
copy of the struct. And because every field is a word, the generator can check
its own field list against `sizeof(struct debug_block)` exactly: if `debug.h`
gains a field and the list does not, the build stops rather than quietly
dropping an entity.

The same header carries the constants the component scales against — travel
times, auto-off limits, the lumbar ceiling — so those come from the build too.

## 3. What Home Assistant sees

One ESPHome external component, `socozi`, owning the SWD link and the poll loop,
plus platform files that hang entities off it.

**Binary sensors** — power, heat, massage, lumbar, moving.

**Sensors** — heat level, massage level, lumbar level, recline position,
headrest position, ADC current, handset frame/error counters, loop ticks, uptime
proxy, settings write/erase/error counters, stops, stalls, arrivals.

**Text sensor** — motion state, decoded from `dbg.motion` to
`idle` / `recline_up` / `recline_down` / `headrest_up` / `headrest_down` /
`flatten`.

**Diagnostic** — link up/down (magic word seen recently), chair firmware
version, ESP's bundled firmware version.

Positions are published as a percentage as well as raw milliseconds, using the
`MOTION_TRAVEL_*_MS` constants carried in the generated header. Those constants
are still guesses, which is a reason to have them come from the build rather
than be typed into YAML.

Everything is read-only in this design. Pressing buttons from Home Assistant
needs a second, *writable* block in RAM with a sequence number the firmware
consumes — a small, self-contained addition, but a separate one, and it changes
the safety argument, because then a bad write can move the chair. Not now.

## 4. Updating the chair

The ESP carries the chair image in its own flash and installs it when the chair
is running something else.

**Bundling.** The firmware build emits `socozi_image.h`: the `.bin` as an
`inline constexpr uint8_t[]` plus its length and version. Inline rather than
static because ESPHome pulls every component header into `esphome.h`, and a
static array there is duplicated per translation unit. The ESPHome build
compiles it in, so one ESPHome OTA delivers both halves and there is exactly one
firmware for the device, as far as Home Assistant is concerned.

**Versioning.** One word, `dbg.version`, so the ESP reads what the chair is
running out of the block it is already polling. A clean tree stamps the git
commit; a dirty one stamps the build time, because two different working trees
at the same commit must not compare equal — see `src/version.h`. The Makefile
holds it in `build/version.txt` rather than recomputing it, so the image the
bridge carries cannot claim a version the firmware inside it was never compiled
with.

**The update entity.** ESPHome's `update` platform, so Home Assistant shows
"SoCozi chair firmware — 1.4 available" with an Install button, and the same
entity reports progress and failure. Optionally auto-install on mismatch,
default off.

**Install sequence.**

1. Refuse unless `dbg.motion == MOTION_NONE`, heat off, massage off, and the
   magic word is current. A reflash mid-motion is the one way this can hurt
   somebody.
2. Set `DBG_CTL` bit 8 (`0x40015804 = 0x100`). That freezes the watchdog while
   the core is halted — set-once until a power cycle, and only writable over the
   debug port.
3. Halt the core.
4. Unlock the FMC, erase the 1 KiB pages the image covers, write it, polling the
   FMC busy flag.
5. **Nothing at or above `0x0800F000`.** That is the settings store: heat and
   massage levels, lumbar firmness, the four presets. The image stops short of
   it and the linker script keeps it that way, so this falls out of the address
   range naturally — but it gets an explicit bounds check in the ESP too,
   because "naturally" is not a safety argument.
6. Read the image back and compare.
7. Reset and run. Confirm the magic word reappears and the version now matches.

**On any failure**, at any step: reset and run anyway. The one outcome that must
never happen is the ESP leaving the chair halted and the user unable to stand
up. If the image is half-written the chair is dead until the next attempt, but
the next attempt is another Install press, not a screwdriver — which is the
entire point of the exercise.

The Bus Pirate route stays as the recovery path, and `make restore-factory`
still exists.

Bit-banged at 500 kHz, writing the current ~10 KiB image is a few seconds, and
even a full 60 KiB would be well under a minute. Words that are already `0xFFFF
FFFF` after the erase are skipped, which takes most of the padding out of that.
Slow enough to want a progress bar, fast enough not to need a RAM-resident flash
loader.

## 5. The SWD transport

About 250 lines of C in the component: line reset, the JTAG-to-SWD sequence,
DP/AP register read and write with turnaround and parity, sticky-error recovery,
and memory read/write through the AHB access port with TAR auto-increment. Two
GPIOs driven through the ESP32-C3's direct output registers.

I looked at pulling in an existing implementation — free-dap is the obvious
candidate, and it is good — but those are all *probe* firmware, implementing
CMSIS-DAP over USB with SWD underneath. Taking the transport out means taking it
out of a build system that does not fit inside ESPHome's, to get a few hundred
lines that are documented in ADIv5 and that we would still have to adapt to our
pin driver. The GD32 flash programming on top is target-specific and would be
ours regardless. So: no vendored C, and the dependency list stays at "ESPHome".

If that proves wrong once it is on the bench, swapping in free-dap is a
contained change — the transport sits behind six functions.

## 6. Repository layout

```
esphome/
  components/socozi/
    __init__.py          config schema, poll interval, pins, the value table
    socozi.h  socozi.cpp component: poll loop, dbg decode, update logic
    swd.h     swd.cpp    SWD transport + GD32 FMC programming
    binary_sensor.py
    sensor.py
    text_sensor.py
    update.py
    socozi_layout.h      <- gitignored, written by the build
    socozi_image.h       <- gitignored, written by the build
  chair.yaml             device config
  secrets.yaml.example   placeholders, copied to secrets.yaml when missing
tools/
  gen-dbg-layout.c       host program, prints the layout header
  gen-image-header.sh    .bin + version -> socozi_image.h
```

The two generated headers sit beside the component's own sources rather than in
`build/` or in a `generated/` subdirectory. ESPHome copies an external
component into its PlatformIO project by enumerating the *top level* of the
component's Python package, so a header anywhere else is simply not copied and
the build fails on the include. Both are gitignored, so nothing generated is
committed; `make esp-clean` removes them.

## 7. Downloading what we need

Nothing is vendored and nothing new is committed except the component's own
source. Everything else is fetched on demand into `build/`, which is already
gitignored:

```make
ESPHOME_VENV = build/esphome-venv
ESPHOME      = $(ESPHOME_VENV)/bin/esphome
ESPHOME_VER  = 2025.7.0      # pinned

$(ESPHOME):
	python3 -m venv $(ESPHOME_VENV)
	$(ESPHOME_VENV)/bin/pip install --quiet esphome==$(ESPHOME_VER)
```

The venv is a make prerequisite, so the first `make esp` builds it and every
later one is a no-op. PlatformIO, the Xtensa/RISC-V toolchain and the ESP-IDF
framework are pulled by ESPHome itself into `~/.platformio` and `~/.esphome`,
which is where those tools already keep their caches and where the user's other
ESPHome projects will share them. Nothing lands in the repo.

Targets:

| | |
|---|---|
| `make esp` | generate headers, build the ESPHome image |
| `make esp-flash` | first-time serial flash over USB-C |
| `make esp-ota` | subsequent updates over wifi |
| `make esp-logs` | ESPHome log stream |
| `make esp-clean` | remove the venv and generated headers |

`make esp` depends on `$(TARGET).bin`, so the chair image bundled into the ESP
is always the one the current tree builds.

`make check` gains a `python3` line alongside the existing compiler and OpenOCD
checks.

## 8. Order of work

1. ~~Pin `_SEGGER_RTT` to a fixed address~~ — publish its address in the debug
   block instead, as `dbg.rtt_cb`. The block is already at a fixed address and
   is already being read every poll, so a pointer in it costs one word and no
   linker surgery. Done.
2. ~~Firmware version word at a fixed flash offset~~ — same reasoning, same
   place: `dbg.version`. Done, encoding in `src/version.h`.
3. `tools/gen-dbg-layout.c` and the generated header. Done.
4. SWD transport on the ESP. Done and working on the chair.
5. Poll loop and the read-only entities. Done.
6. GD32 flash programming and the `update` entity. Done. The chair has been
   reflashed from Home Assistant, and the settings store survived it.

Both debug-block additions are behind `BRIDGE`, a build option like `RTT`.
`make reference` builds with `BRIDGE=0`, so the fallback image's RAM layout is
untouched by any of this.

## 9. What is proven

`make ci-esp` builds the chair firmware, generates both headers from it, and
compiles the ESP image around them, from a clean tree with no manual step. That
much is checked on every push.

On the chair: the transport, the block read and every entity, and the whole
install path — halt, erase, program, verify, reset — with the chair reflashed
from Home Assistant and the settings store intact afterwards.

Two things were wrong on the first attempts, both worth keeping written down
because neither would have been found by reading the code:

- `CSW_WORD_FIXED` was `0x23000050`. The low three bits are the access size and
  zero means *byte*, so every single-word register access was an 8-bit
  transfer. Block reads use the other constant and worked throughout, so this
  only broke the flashing path — the DHCSR write never took and the core never
  halted. It is `0x23000002`.
- Flash pages are **1 KiB**, not the 4 KiB assumed everywhere. Erasing
  `0x08000000` and then programming `0x08000400` returns PGERR, which pins it
  exactly. This was wrong in the chair firmware too: `settings.c` would have
  erased a quarter of the store it thought it had, though only after 128
  records, which had never happened.

The Bus Pirate and `make restore-factory` remain the recovery path if an
install ever leaves the chair half-written.
